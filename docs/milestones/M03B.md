# M03B — CTR baselines and shopper-intent ablation

**Status:** Implementation delivered; full-data experiment and interpretation pending.

## Research question

Does the M03A behavioral feature family improve prediction of observed ad clicks beyond static user/ad context? This is an **associational offline CTR** study, not an ad-lift or policy evaluation.

## Dataset and isolation

- Input: `artifacts/m03a/train_features.csv`, `validation_features.csv`, and `sample_manifest.json`.
- The published Taobao `test.csv` is never read by this milestone.
- M03A row-index hash split is deterministic but **not chronological or user-disjoint**. No verified impression timestamps are available. Historical sequences' point-in-time correctness is unverified.
- No features are derived from `clk` except the supervised label. No fit on validation labels except LightGBM's early-stopping model selection.

## Model specifications

| ID | Algorithm | Feature family | Implementation |
|---|---|---|---|
| M0 | Hashed logistic regression | 16 static categorical fields + price | `FeatureHasher` 2^18 bins, `SGDClassifier(loss=log_loss)`, one streaming epoch, alpha 1e-5, log1p price |
| M1 | LightGBM | Same static fields | Categorical IDs mapped to train-fitted consecutive integer codes (unknown validation IDs = -1) and declared categorical; 250 max trees, 31 leaves, 0.05 learning rate, 25-round early stopping |
| M2 | LightGBM | M1 plus six behavioral features | Same hyperparameters and validation protocol as M1 |

Categorical IDs are **not ordinal**. Train-fitted integer encoding avoids hash collisions; unseen validation categories are treated as missing. **Encoding maps are not yet persisted with model artifacts, so models are not serving-ready.** The LightGBM implementation materializes float32 feature matrices in memory: it is intended for the ~1.1M-row M03A sample, **not** the 21.9M-row source CSV. M0 uses an out-of-core pass, whereas M1/M2 read prepared CSVs into memory. This comparison measures an algorithmic and feature-family difference; M1 vs M2 is the controlled feature ablation.

## Metrics and acceptance criteria

- Primary: validation binary log loss (lower is better).
- Secondary: ROC-AUC, average precision / PR-AUC, Brier score, mean predicted CTR, and equal-width probability calibration bins.
- Report each model's exact results. Do not assert an improvement until observed. In particular, M0 is **not** a controlled feature ablation against M2 because the algorithms differ.
- Unit tests and a tiny synthetic end-to-end run must pass before running the full sample.
- Record run commands, Python/package versions, hardware, runtime, and `metrics.json` SHA-256 in `docs/experiments/M03B-results.md` after the user's actual full-data run.

## Reproduce

```bash
python -m pip install -e '.[dev,ml]'
pytest
python -m sponsored_ads.ctr_train_cli --input-dir artifacts/m03a --output-dir artifacts/m03b
```

Outputs (ignored by Git): `artifacts/m03b/metrics.json`, `m0_logistic.joblib`, `m1_lightgbm_static.txt`, `m2_lightgbm_intent.txt`. The `metrics.json` contains the SHA-256 of the M03A manifest, seed, settings, caveats, and per-model calibration bins. Model artifacts alone are **not** serving-ready: a production scoring wrapper must reproduce categorical hashing, feature order, and numeric preprocessing.

## Known threats to validity

- Source click labels reflect the original ad-serving policy; missing candidate impressions are not negatives.
- User/ad overlap across development splits may inflate performance.
- The published history fields might contain information unavailable at serving time; there is no timestamp to audit this.
- Offline CTR metrics do not establish revenue lift, auction correctness, budget pacing performance, or causal impact.
- This stage does not tune hyperparameters or perform calibrated probability post-processing; calibration is **measured**, not guaranteed.
