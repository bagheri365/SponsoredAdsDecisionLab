# M04B — Behavioral retrieval and candidate fusion

**Status:** implementation delivered; full-data integration and evaluation pending.

## Objective

Add a deterministic, explainable shopper-affinity retrieval channel and combine it with M04A impression-count popularity. This is a **reconstructed observed-ad catalog** experiment, not a historical eligible-ad retrieval system.

## Input and contracts

`ObservedAd(adgroup_id, cate_id, brand, impressions)` represents an ad catalog row. `ShopperHistory(cate_his, brand_his, btag_his)` represents aligned `^`-separated behavioral sequences from TaobaoAd_x1. `RetrievedAd` contains a stable ad ID, a source-specific score, and source attribution.

`BehavioralIndex` builds in-memory inverted lists by category and brand. `affinity` scores each matching ad using the sum of category and brand matches, with recency weights `(position + 1) / history_length`; later positions are **assumed** to be more recent. The source dataset does not independently verify sequence ordering or point-in-time safety. `btag_his` is validated for alignment but is not used for event weighting in this first version: assigning purchase/cart weights without verified event semantics would introduce unjustified assumptions.

`popularity` ranks by observed training impression counts. `fuse_ranked` uses reciprocal rank fusion with `rrf_k=60` so scores from the two channels need not be calibrated or directly comparable. It deduplicates ad IDs, preserves source attribution, applies explicit exclusions, and uses ad ID as a deterministic tie-break. `retrieve_fused` exposes the end-to-end API.

## Example

```python
from sponsored_ads.behavioral_retrieval import BehavioralIndex, ObservedAd, ShopperHistory, retrieve_fused

index = BehavioralIndex([ObservedAd("ad-1", "category-1", "brand-1", 12)])
history = ShopperHistory.from_delimited("category-1", "brand-1", "1")
print(retrieve_fused(index, history, top_k=1))
```

## Validation

Run `pytest tests/test_behavioral_retrieval.py` and `pytest`. Tests cover alignment, recent-match weighting, empty histories, exclusions, stable ordering, fusion, duplicate detection, and invalid inputs. This patch deliberately does not modify the M04A catalog JSON schema or assume its on-disk representation; the production adapter must be added and tested against the actual saved catalog before a real-data run.

## Experimental protocol (future M04C)

1. Partition the published training impressions into a fixed development-build and held-out evaluation subset **before** aggregating the catalog. Do not evaluate on rows used to build popularity counts.
2. Build both channels from the build subset only. Use the held-out impression's supplied histories as request context, with the explicit caveat that history point-in-time validity is unverified.
3. Report observed-click Recall@K, catalog coverage, eligible-filter proxy coverage, latency, empty-history behavior, and comparisons with popularity-only. Keep published `test.csv` untouched.
4. Do not treat unshown ads as negatives or claim unbiased retrieval recall, causal lift, or verified request-time eligibility.

## Scalability and limitations

The in-memory index holds all observed ad IDs and inverted lists. Large categories may produce large intermediate candidate sets. Benchmark memory and latency before choosing a production-oriented top-N postings strategy. Training-aggregate impression counts are not point-in-time features. Synthetic auction eligibility, bids, and budgets are separate future components.
